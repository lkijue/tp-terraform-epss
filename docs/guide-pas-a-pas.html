Projet CloudTech · Azure for Students · Terraform

Déployer l'infra multi-environnement, clic par clic

Le code Terraform est déjà écrit et testé dans Downloads\terraform-azure-project. Ce guide te fait installer les outils, brancher Azure, GitHub et HCP Terraform, déployer l'environnement dev, le tester, puis tout détruire. Coche chaque case au fur et à mesure : ta progression reste enregistrée dans ce navigateur.

Remplis ces champs quand tu les connais (étapes 3 et 5) : les commandes en jaune se mettent à jour toutes seules.

    Vue d'ensemble

    2 min de lecture

    Ce qui sera créé

    Par environnement : 1 Resource Group, 1 VNet + 2 subnets, 2 NSG, 1 IP publique, 1 Load Balancer, 2 VMs web nginx, 1 VM PostgreSQL, 1 Storage Account, 1 Key Vault.

    Qui fait quoi

    GitHub garde le code et lance la CI. HCP Terraform garde le state et exécute plan / apply sur Azure. Toi, tu cliques sur « Confirm & apply ».

    Budget

    Environ 1,5 $ par jour par environnement allumé. Sur 100 $, aucun risque si tu détruis après chaque session (étape 15).

    Quota étudiant

    Un environnement = 3 vCPU. Déploie un seul environnement à la fois : dev, puis staging, puis prod.

    Installer Terraform et Azure CLI

    ~10 min

    Git et VS Code sont déjà sur ton PC. Il manque terraform et az (exercice 01 du sujet).

    • Ouvre le menu Démarrer, tape PowerShell, clique sur Windows PowerShell. Colle ces deux commandes (accepte les conditions de winget si on te le demande avec Y) :

az version
      Tu dois voirTerraform v1.x et un bloc JSON avec "azure-cli": "2.x".
      Si ça bloque

      « terraform n'est pas reconnu » : redémarre le PC. Si winget n'existe pas, installe « App Installer » depuis le Microsoft Store.

    04

    Créer ta clé SSH et noter ton IP

    ~5 min

    Les VMs n'acceptent que la connexion par clé SSH, et seulement depuis ton adresse IP.

    • Crée une clé (appuie 3 fois sur Entrée : emplacement par défaut, pas de phrase secrète) :

      ssh-keygen -t ed25519
      Si « already exists. Overwrite? »

      Tape n : tu as déjà une clé, on la réutilise.

    • Affiche la clé publique et garde-la sous la main (elle commence par ssh-ed25519, c'est la seule qu'on donne à Azure ; ne partage jamais le fichier sans .pub) :

      Get-Content $HOME\.ssh\id_ed25519.pub

    • Affiche ton IP publique au format attendu :

      "$(Invoke-RestMethod https://api.ipify.org)/32"
      Tu dois voirQuelque chose comme 88.123.45.67/32. Note-le.
      À savoirSi tu changes de réseau (école ↔ maison), ton IP change : il faudra mettre à jour la variable allowed_ssh_cidr dans HCP Terraform (étape 8) et relancer un apply pour que SSH fonctionne. Le site web, lui, reste accessible partout.

      Envoie la modification sur GitHub, sur les deux branches :

git commit -am "chore: organisation HCP Terraform"
git push
git checkout main
git merge develop
git push
git checkout develop

      terraform login

      Tape yes. Une page s'ouvre : clique Create API token, copie le jeton, colle-le dans le terminal (rien ne s'affiche, c'est normal) puis Entrée.

    Déployer l'environnement dev

    ~15 min

    • Workspace cloudtech-dev → bouton New run (en haut à droite) → Run type Plan and apply → Start.

    • Attends la fin du Plan (1-3 min ; le premier run enregistre des fournisseurs Azure, il peut être plus long).

      Tu dois voir« Plan: 38 to add, 0 to change, 0 to destroy ». Capture d'écran : c'est ton terraform plan.

    • Clique Confirm & apply, ajoute un commentaire (ex : « premier déploiement dev ») → Confirm plan. L'apply dure 5 à 10 minutes.

      Tu dois voir« Apply finished », puis dans l'onglet Outputs : website_url, lb_public_ip, ssh_commands, ssh_db_command…
      Erreurs fréquentes

      RequestDisallowedByPolicy : région non autorisée → étape 3, change location, commit + push sur develop, relance un run.

      QuotaExceeded ou « cores » : un autre environnement tourne encore → détruis-le (étape 15).

      SkuNotAvailable : B1s indisponible dans la région → autre région (étape 3).

      MissingSubscriptionRegistration : relance simplement un run quelques minutes plus tard (Azure finit d'activer un service).

      Le plan échoue sur l'organisation : vérifie que REMPLACE-MOI a bien été remplacé et poussé sur develop (étape 5).

    Tester l'infrastructure

    ~20 min

    Ce sont les tests demandés par le sujet. Attends 3 minutes après l'apply : les VMs installent nginx et PostgreSQL au démarrage. Fais une capture de chaque résultat.

    • Site via le Load Balancer : ouvre l'URL de l'output website_url dans ton navigateur.

      Tu dois voir« cloudtech · environnement dev » et « Servi par la VM : web-1 » (ou web-2).

    • Tests automatiques (state, Azure CLI, répartition de charge, ports SSH). D'abord, récupère le state depuis HCP Terraform, puis lance le script :

      git pull
terraform -chdir=environments/dev init
powershell -ExecutionPolicy Bypass -File .\tests\smoke-test.ps1 -Environment dev
      Tu dois voirLa liste du state, les 3 VMs « VM running », web-1 et web-2 qui se partagent les requêtes, puis « TOUS LES TESTS SONT PASSÉS ».

    • Commandes du sujet (vérification du state et Azure CLI) :

      terraform -chdir=environments/dev state list
terraform -chdir=environments/dev state show 'module.compute.azurerm_linux_virtual_machine.web[0]'
az vm list --resource-group rg-cloudtech-dev --output table
az network lb list --resource-group rg-cloudtech-dev --output table

    • SSH vers web-1 (copie la 1re commande de l'output ssh_commands, réponds yes la première fois) :

      terraform -chdir=environments/dev output ssh_commands

      Une fois connecté, vérifie qu'on joint la base depuis le web (remplace l'IP par l'output db_private_ip, souvent 10.10.2.4), puis quitte :

      nc -zv 10.10.2.4 5432
exit
      Tu dois voir« Connection to 10.10.2.4 5432 port [tcp/postgresql] succeeded! ». Si nc n'existe pas : timeout 3 bash -c '</dev/tcp/10.10.2.4/5432' && echo OK

    • SSH vers la base (rebond par web-1, la db n'a pas d'accès direct) : lance la commande de l'output ssh_db_command, puis sur la VM db :

      sudo cat /var/log/init-postgres.log
sudo -u postgres psql -c '\du'
exit
      Tu dois voir« PostgreSQL prêt » et un rôle app dans la liste. Cela prouve que la VM a lu son mot de passe dans le Key Vault (aucun secret en clair).

    • Sécurité réseau : depuis ton PC, la base doit être injoignable et SSH refusé si tu n'es pas sur ton IP. Les NSG le garantissent ; tu peux le montrer dans le portail : Resource Group rg-cloudtech-dev → nsg-cloudtech-dev-db → Règles de sécurité de trafic entrant.

    • Network Watcher : dans la barre de recherche du portail Azure, tape Network Watcher → Topologie → choisis ton abonnement et le Resource Group rg-cloudtech-dev.

      Tu dois voirLe schéma VNet → 2 subnets → NICs → VMs, le Load Balancer et les NSG. Capture pour le dossier.

    • Portail Azure : ouvre rg-cloudtech-dev et fais une capture de la liste des ressources.

    Points à savoir expliquer

    • Pourquoi aucune VM n'a d'IP publique (une seule IP : le Load Balancer ; SSH via NAT 2201/2202 ; sortie Internet par l'outbound rule).

    • Comment le mot de passe PostgreSQL arrive sur la VM sans être en clair (random_password → Key Vault → identité managée → lecture au démarrage).

    • Pourquoi le state est dans HCP Terraform (chiffré, verrouillé pendant un run, historique des versions, partagé en équipe).

    • Les limites et améliorations : voir le tableau en fin de docs/security.md (OIDC au lieu du secret, Private Endpoints, Bastion, HTTPS).

    • Complète docs/fiche-mission.md (ta tâche individuelle) avant le rendu.
